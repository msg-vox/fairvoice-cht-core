# CHT Core changes: mid-form Enketo language switching

This document describes the smallest change to CHT Core needed to let an
interviewer switch the language of an **already-open** Enketo form, without
losing answers.

This is the "Option 1" approach from the investigation: expose the language
selector that Enketo already supports natively.

## Summary

CHT passes the app language to Enketo once, when the form is created:

```ts
// webapp/src/ts/services/enketo.service.ts
return new window.EnketoForm(form, options, { language: userSettings.language });
```

Enketo can switch language at runtime, but CHT does not give it a place to put
the language selector. The form wrapper needs a `.form-language-selector`
container. Enketo finds that container, moves its own hidden `#form-languages`
`<select>` into it, and un-hides it when the form has more than one language.

Two template edits are required:

1. `webapp/src/ts/components/enketo/enketo.component.html` (all normal WebApp forms)
2. `webapp/web-components/cht-form/src/app.component.html` (the standalone `cht-form` web component)

No TypeScript, API, form, or `app_settings` changes are required.

## Why this has to be a CHT Core change

The language selector cannot be added from a CHT project, `cht-conf`, a UI
extension, or an XLSForm:

- `cht-conf` uploads forms, settings, resources, and route-level UI extensions.
  It cannot change the WebApp form wrapper.
- UI extensions are mounted as their own route tab, not while a form is open,
  and they have no access to the live Enketo form instance.
- XLSForm has no way to add DOM elements or to switch Enketo's current language.

## What Enketo already provides

CHT Core currently uses `enketo-core` 7.2.5 (`webapp/package.json`). Its
language module is at `webapp/node_modules/enketo-core/src/js/language.js`.

On form init it does approximately this:

```js
const root = this.form.view.html.closest('body') || this.form.view.html.parentNode;
const langSelector = root.querySelector('.form-language-selector');
const formLanguages = this.form.view.html.querySelector('#form-languages');

if (langSelector) {
  langSelector.append(formLanguages);
  if (this.languages.length > 1) {
    langSelector.classList.remove('hide');
  }
}
```

- `#form-languages` is the language `<select>` generated by Enketo from the
  form's `<itext><translation lang="...">` blocks.
- If `.form-language-selector` exists, the select is moved into it and shown
  when there are at least two languages.
- If `.form-language-selector` does **not** exist, the select stays inside the
  form. CHT then hides it with this existing rule:

  ```less
  // webapp/src/css/enketo/medic.less
  .enketo {
    form {
      #form-languages {
        display: none;
      }
    }
  }
  ```

- When the user changes the select, Enketo calls `form.langs.setFormUi(lang)`
  (see `src/js/language.js`). That:
  - toggles the `.active` class on already-rendered `[lang]` labels,
  - updates choice labels in `<select>`/`<datalist>` elements,
  - sets the form `dir` for RTL languages,
  - updates repeat instances,
  - sets `window.enketoFormLocale`,
  - dispatches Enketo's `ChangeLanguage` event, which triggers
    `form.output.update()`, the table of contents, and widget updates.
  - It does **not** reset the form model, so in-progress answers are preserved.

## Change 1: WebApp `mm-enketo` wrapper

**File:** `webapp/src/ts/components/enketo/enketo.component.html`

Current template:

```html
<div [attr.id]="formId" class="enketo" [attr.data-editing]="editing">
  <div class="container pages"></div>
  <ng-content select="[duplicate-contacts]"></ng-content>
  <div class="form-footer">
    ...
  </div>
</div>
```

Add the selector container before the `.container`:

```diff
 <div [attr.id]="formId" class="enketo" [attr.data-editing]="editing">
+  <div class="form-language-selector hide"></div>
   <div class="container pages"></div>
   <ng-content select="[duplicate-contacts]"></ng-content>
   <div class="form-footer">
```

This covers all forms rendered through `mm-enketo`:

- contact create/edit/report forms
- report add/edit forms
- task forms
- training-card forms

### Important placement rules

- It must not be inside `.container.pages`. `EnketoService.renderFromXmls()`
  replaces that element's contents with the form HTML, which would wipe the
  selector container.
- It must not be inside the `<form>` element. The existing
  `form #form-languages { display: none; }` rule in
  `webapp/src/css/enketo/medic.less` would keep the select hidden even after
  Enketo moves it.
- Keep the `hide` class. Enketo removes it only when the form has two or more
  languages, so single-language forms show nothing.

## Change 2: standalone `cht-form` web component

**File:** `webapp/web-components/cht-form/src/app.component.html`

Current template:

```html
<div [attr.id]="formId" class="enketo" [attr.data-editing]="editing">
  <div class="container pages"></div>
  <div class="form-footer">
    ...
  </div>
</div>
```

Add the same container, with the same placement rules:

```diff
               <div [attr.id]="formId" class="enketo" [attr.data-editing]="editing">
+                <div class="form-language-selector hide"></div>
                 <div class="container pages"></div>
                 <div class="form-footer">
```

This is only needed if the standalone web component should also offer
mid-form language switching. It does not affect the normal CHT WebApp.

Note: `webapp/web-components/cht-form/src/index.html` contains a hidden
`#form-languages` placeholder. That is a demo/host-page element and is
unrelated; Enketo uses the `#form-languages` inside the form HTML.

## No other changes are required

- No `EnketoService` changes.
- No TypeScript type changes.
- No `app_settings` changes.
- No XLSForm changes.
- No form version bumps.
- No translations to upload.

The selector is created by Enketo from the form's existing
`<itext><translation lang="...">` blocks. A form that already opens in the
correct language will show the selector with the same languages.

## Optional CSS

The Enketo core styles for `.form-language-selector` and `#form-languages` are
already included through `webapp/src/css/enketo/enketo.scss` (imported by
`medic.less`). The default placement is at the top of the form, before the
`.container`, with a small left margin.

If the default spacing looks wrong inside a CHT form or modal, add a scoped
override to `webapp/src/css/enketo/medic.less` rather than changing Enketo
styles, for example:

```less
.enketo .form-language-selector {
  padding: 8px 16px 0;
  margin-left: 0;
}

.enketo .form-language-selector #form-languages {
  margin-left: 0;
}
```

Do not add `display: none` to `#form-languages` outside a `form` selector.

## Gotchas

- **Multi-instance `cht-form` pages:** Enketo looks up
  `.form-language-selector` from `closest('body')`, not from the individual
  form. If a host page embeds several `cht-form` elements at once, all of them
  will find the first selector. This is an existing Enketo limitation. For the
  main WebApp only one form is open at a time, so it is not a problem there.
  If `cht-form` must support multiple simultaneous forms, the correct fix is
  upstream in Enketo: scope the selector lookup to the form's container.
- **Form title:** CHT sets `#form-title` from the app translation at render
  time (`EnketoService.setFormTitle`). Switching only the form language does
  not retranslate the title. The Cancel/Previous/Next/Submit buttons are also
  app-translated and stay in the app language. The questions, choices, hints,
  validation messages, and form body switch as expected.
- **App language and form language are independent:** this change gives the
  form its own selector. Changing the app's top-right language menu still
  affects the next form opened; it does not change an open form (that is the
  separate "Option 2" change described below).
- **Locale-sensitive XPath:** `window.enketoFormLocale` changes when the user
  switches. Expressions using locale-sensitive functions (for example date or
  number formatting) may produce different results after the switch.
- **Calculations are not recalculated** by `setFormUi`. Do not call
  `forceRecalculate()` on language change; recalculating could change answers.
- **Language code matching:** the form language IDs must match the XForm
  `<translation lang="...">` values exactly (for example `en`, `hi`, `ne`,
  `fr`, not `Hindi (hi)`).
- **The chosen language is not submitted** with the report. If the project
  needs to know which language an interview was conducted in, add an explicit
  XLSForm question or a hidden field set when the language changes.

## Verification in CHT Core

### Build

From the CHT Core checkout:

```sh
cd webapp
npm ci
npm run build            # normal WebApp
npm run build:cht-form   # only if change 2 is included
```

### Unit tests

The existing Enketo/component tests should still pass:

```sh
cd webapp
npm run unit
npm run unit:cht-form    # if change 2 is included
```

Optionally add a small template assertion that
`.form-language-selector.hide` exists in the `mm-enketo` component test.

### Manual test matrix

Use a deployed form with at least two form languages, for example the HREDD
survey (`en`, `hi`, `ne`) or a COTE form (`en`, `fr`).

1. **Two-language form**
   - Open a new form.
   - The app language is used initially.
   - The language selector is visible at the top of the form.
   - Switching language updates question labels, hints, choices, validation
     messages, and the form direction without clearing answers.
   - The form can be submitted normally.
2. **Single-language form**
   - Open an English-only form.
   - No empty language selector is shown.
3. **Mid-form switching**
   - Answer several questions, including a `select_one`, a `select_multiple`,
     a repeat group, and a text question.
   - Switch language.
   - Confirm all answers and repeat instances are preserved.
   - Confirm choice labels and select options update.
   - Move between form pages after switching.
4. **Validation**
   - Trigger a required-field or constraint error.
   - Switch language.
   - Confirm the validation message is shown in the new language.
5. **RTL** (if applicable)
   - Confirm the form `dir` and layout update when switching to an RTL
     language.
6. **Modal forms**
   - Repeat the basic switch check in a contact form, report form, task form,
     and training-card form, since they share `mm-enketo`.
7. **Offline**
   - Repeat on an offline device. No network calls are involved.

## Optional follow-ups (not part of this change)

### App language menu drives the open form

If the top-right app language menu should also switch an open form, the core
change is:

1. Add a method to `EnketoService`:

   ```ts
   setLanguage(code: string): boolean {
     const form = this.getCurrentForm();
     if (!form?.langs?.languagesUsed?.includes(code)) {
       return false;
     }
     form.langs.setFormUi(code);
     return true;
   }
   ```

   `getCurrentForm()` already exists in `enketo.service.ts`.

2. Call it from `SetLanguageService.set()` after
   `globalActions.setLanguage(...)`, or subscribe to the language store
   selector from `EnketoComponent`.

3. If UI extensions also need to react, dispatch a
   `cht-language-changed` event from the same place:

   ```ts
   document.dispatchEvent(new CustomEvent('cht-language-changed', {
     detail: { code },
   }));
   ```

   The shared reporting shell currently listens on the extension element
   itself (`projects/shared-reporting/shell.js`), not on `document`. Either
   change that listener to `document`, or have the UI-extension host
   re-dispatch the event on each extension element. Also note that the event
   currently has no producer in CHT Core; it is only simulated in the project's
   test harness.

### `cht-form` language input

For the standalone web component, a dedicated input is cleaner than reusing
`user.language`:

```ts
@Input() set language(code: string) {
  this.enketoForm?.form.langs.setFormUi(code);
}
```

Do not implement this by changing the existing `user` input. `set user` calls
`queueRenderForm()`, which unloads and rebuilds the Enketo form and loses
in-progress answers.

## Acceptance criteria

- A form with two or more `<translation lang="...">` blocks shows a language
  selector inside the form.
- A form with one language shows no selector.
- Switching language mid-form preserves all answers and repeat instances.
- Labels, hints, choices, constraint messages, and directionality update.
- No Enketo form model reset, no extra report fields, and no new network calls.
- `npm run build` and the WebApp unit tests pass.
- The existing `form #form-languages { display: none; }` rule remains untouched,
  because the selector is moved outside the `<form>`.

## Version checked

The paths and Enketo behaviour above were checked against:

- CHT Core `4.x`
- `enketo-core` 7.2.5 (the version declared by CHT Core 5.3.3)
