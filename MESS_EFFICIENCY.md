# Fairvoice data messaging efficiency

The server stores one immutable CouchDB document per message in a dedicated database. Both participants use the same canonical ID, and an offline send can retry with that ID after a lost response. The client groups messages by the other participant’s account ID, which preserves the thread when a user changes assignments. Keep this structure. The main opportunities are in how often the API and client read, transfer, and process the same data. These findings come from source review. A deployment benchmark is still to be run. [Message storage and sync](api/src/services/data-messaging.js#L246) · [Messaging implementation](MESS_DATA_IMPLEMENTATION.md)

## Findings and proposed changes

1. **Send recipient directories only when they change.** Every sync page fetches and returns the full recipient directory, including idle polls and each page of a catch-up. Let the client supply its cached directory revision and omit entries when the revision matches. Keep responses compatible with callers that supply no revision. Preserve the distinction between an unpublished directory, an unchanged directory, and a published empty directory. Offline users need to retain the last published snapshot until a replacement arrives. [Server sync](api/src/services/data-messaging.js#L273) · [Local checkpoint](webapp/src/ts/services/data-messaging-directory.service.ts#L20)
2. **Refresh the UI only when visible messaging data changes.** Offline sync notifies subscribers on completion, even on an idle poll. The inbox, open thread, and unread badge can then independently reread history. Save cursor advances even when the visible data is identical. Notify subscribers when a message, directory, or delivery state changes, including progress saved before a partial sync failure. Share the account’s history read across consumers responding to the same refresh. [Offline sync](webapp/src/ts/services/data-messaging-sync.service.ts#L36) · [History reads](webapp/src/ts/services/data-messaging-history.service.ts#L57) · [Unread count subscription](webapp/src/ts/services/unread-records.service.ts#L127)
3. **Limit thread detail work to the selected peer.** Opening a thread currently builds and sorts every conversation and checks read markers across incoming history before selecting the peer. Add a thread-specific read path that checks markers and sorts only that peer’s messages. It can start by filtering shared in-memory history. Evaluate a persisted local index if profiling still shows local reads dominate. [Thread loading](webapp/src/ts/modules/messages/messages-content.component.ts#L201) · [Conversation grouping](webapp/src/ts/services/data-messaging-conversations.service.ts#L35)
4. **Remove reconciled outbox copies.** Pending upload checks scan the full local outbox, including sent messages that also exist in canonical history. Remove a local outbox record once its matching canonical message is durable. An upload acknowledgement alone can precede local history persistence. Keep waiting records, rejected text, and any outbox payload that conflicts with a canonical record using the same ID. Allow interrupted cleanup to retry safely. [Outbox and accepted history](webapp/src/ts/services/data-messaging-store.service.ts#L54)

The server’s 100-message page size caps matching results. CouchDB still evaluates the participant selector against changes across the database. Measure cold starts and catch-up as unrelated message traffic grows. If cold history loads dominate, evaluate a participant-indexed history query. Keep the CouchDB sequence cursor for incremental sync, and test any handoff between indexed history and incremental sync with concurrent writes. A message composed while offline can reach the server after newer messages, so the composition timestamp is suitable for display order and the sequence cursor tracks delivery progress. [Sync page query](api/src/services/data-messaging.js#L284) · [CouchDB changes feed](https://docs.couchdb.org/en/stable/api/database/changes.html) · [Late-upload integration test](api/tests/integration/data-messaging.spec.js#L170)

## Benchmark setup

- Use a disposable instance of this Fairvoice branch with real CouchDB, the default CHT configuration, and data messaging enabled. For a source build, follow the CHT development setup and the Node and npm versions in `package.json`. Run CouchDB, build the webapp, and start the API and Sentinel. Use the same build mode and service configuration for the baseline and each candidate. [CHT development setup](https://docs.communityhealthtoolkit.org/community/contributing/code/core/dev-environment/) · [Runtime requirements](package.json#L10)
- Run `node scripts/seed-data-messaging.js` from the repository root with the instance’s `COUCH_URL` and `API_PORT`. The script replaces the pilot setting and creates an offline worker, an online-only dashboard user, and an unrelated control account. Use separate Chrome profiles for the worker and dashboard. Browser offline mode and throttling cover the first round. Use a representative Android device and the Fairvoice build when measuring WebView performance or Firebase push. [Desktop smoke test](MESS_DATA_IMPLEMENTATION.md#L153) · [Android push setup](plans/firebase-setup.md)
- Extend the fixture generator with a fixed seed and independent sizes for history per account, messages per thread, recipients per account, and total unrelated message traffic. Include a busy supervisor with many eligible recipients, a worker with a long thread, and a separate branch producing unrelated traffic. Record the dataset sizes and calibrate them against expected pilot usage. Use synthetic accounts and message text.
- Restore equivalent data and starting cursors before comparing runs. Record the Git revision, CouchDB version and topology, browser or device, network profile, and whether the client cache is cold or warm. Report the number of runs, median and p95 latency, transferred bytes, and request or storage-operation counts. Keep API timings and browser timings so server waits and client processing can be diagnosed independently.

## Experiments

| Scenario | Workload and measurements |
| --- | --- |
| Idle sync | Poll with no new participant messages across small and large unchanged directories. Record response bytes, latency, directory lookups, and UI refreshes. Update or clear the directory and check that the next sync applies the change. |
| Fresh dashboard session | Start with an empty browser messaging session. Hold the target account’s history fixed while increasing unrelated history. Record time to first usable inbox, total sync time, page count, and API latency. |
| Offline catch-up | Keep the worker’s cache and cursor, disconnect, then add several pages of incoming messages and queue outgoing messages. Reconnect under controlled throttling. Record time to finish, pages, bytes, and local writes. Interrupt a run mid-page and verify recovery after restart. |
| Opening one thread | Use a warm offline cache and a busy inbox. Hold the selected thread size fixed while growing other conversations. Record time to render, PouchDB reads, and the number of read-marker keys requested. |
| Pending uploads after many sends | Hold the number of waiting messages fixed while growing reconciled outbox history. Record pending-query latency, local record count, and storage footprint before and after cleanup. |

## Regression checks

- Verify participant-only history and directory ownership, including the unrelated control account. Verify that accepted history survives reassignment or pilot disablement. Keep the API’s live eligibility check for new sends.
- Verify that late uploads and retries retain the original ID, replay after partial persistence, and appear once per participant. Include an older message composed offline and accepted after newer messages, plus a lost upload acknowledgement and a conflicting payload with the same ID.
- Verify directory refresh after a rename or reassignment, an explicitly empty directory, preservation of the cached directory during a failed refresh, and compatibility with clients that send no directory revision.
- Verify thread ordering, unread counts, and delivery status before and after each change. Check that reconciled sends remain visible after outbox cleanup and that rejected text remains recoverable.
- Reuse the CouchDB-backed API and browser sync suites for focused regression coverage. Use the WebdriverIO messaging test as the starting point for the cross-account and offline flows.
